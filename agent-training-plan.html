SQLite Training Loop Post-Mortem

Date: 2026-03-15  |  Run: parallel-20260315-121312/sqlite  |  Result: 0 keeps, 3 timeouts, 5 rounds

1. What Happened

The agent training loop iteratively edits an AI agent's instruction file (the "trainee") to improve its performance on a benchmark task. A second AI (the "editor," Claude Sonnet) reads scores and missed-finding data, proposes one change to the instruction file, and the trainee (Claude Haiku) reruns the benchmark. If the score improves, the change is kept; otherwise it is discarded.

The SQLite benchmark asks the trainee to read four technical documents (1,438 total lines) about SQLite internals and extract structured findings, cross-references, and documentation gaps into JSON. A rubric with 32 expected findings, 3 expected cross-references, and 3 expected gaps scores the output across seven dimensions.

The baseline (round 0) scored 0.886 composite in 198 seconds. This is already high: 30 of 32 findings matched, verbatim accuracy was perfect, all categories covered. The only zero was gap_detection. The loop then ran 5 rounds with zero successful improvements:

2. Why Did 3 of 5 Rounds Time Out?

The 300-second timeout was calibrated for the ESP32-S3 benchmark (1,173 lines across 5 files). The SQLite benchmark is 23% larger (1,438 lines across 4 files), which alone pushes execution time closer to the limit. The baseline already took 198 seconds — 66% of the budget with no extra instructions.

Each editor change added work. Round 1 added a prose extraction emphasis, likely adding a second pass over all prose paragraphs. Round 3 (which did complete, at 363s — over the limit) added table-row emphasis that produced more findings (115 vs 86 baseline) but took significantly longer. Round 4 raised the extraction target, encouraging the agent to do more re-reading. Round 5 changed the model to Sonnet, which is slower per token.

Root cause: The timeout margin was only ~100 seconds (300s budget minus 198s baseline = 102s slack). Any instruction change that adds even one additional read-verify cycle per source file (4 files × ~25s each) exhausts this margin. The instructions already mandate multiple expensive steps: re-reading every excerpt for verbatim verification, JSON validation, 5-finding spot-checks, and a 20-gap expansion pass. Adding more thoroughness on top of this pushes Haiku past the wall.

The coroutine 'ClaudeSDKClient.interrupt' was never awaited warning suggests the timeout kill is not cleanly handled — the SDK's interrupt coroutine is created but not awaited, which is a minor bug in the loop harness.

3. Why Did gap_detection Stay at 0.0?

This is a rubric calibration problem, not a trainee performance problem.

The scorer works by keyword matching: it splits each expected gap description into words longer than 4 characters, then checks what fraction appear in the scout's gap text. A match requires >40% of key terms to appear. The rubric defines three expected gaps:

G001: "No documentation on encryption or the SQLite Encryption Extension (SEE)"
Key terms: documentation, encryption, sqlite, encryption, extension, (see) — 6 terms
Scout matched: "documentation", "sqlite" = 2/6 = 33% — FAIL
G002: "No documentation on FTS5 full-text search internals, tokenizers, or ranking"
Key terms: documentation, full-text, search, internals, tokenizers, ranking — 6 terms
Scout matched: "documentation" = 1/6 = 17% — FAIL
G003: "No documentation on the online backup API (sqlite3_backup_init, step, finish)"
Key terms: documentation, online, backup, (sqlite3_backup_init,, step,, finish) — 6 terms
Scout matched: "documentation" = 1/6 = 17% — FAIL

The scout DID produce 22 gaps covering missing examples, missing benchmarks, missing error handling, and more. But none mentioned encryption/SEE, FTS5, or the backup API specifically. These expected gaps describe topics entirely absent from the source documents. The scout cannot know to mention "encryption" or "FTS5" unless it has prior knowledge of SQLite's full feature surface — the four source documents simply never mention these features. The agent instructions tell it to look for gaps in what IS documented, not to hypothesize about what an ideal documentation set would cover.

The gap_detection dimension is effectively unwinnable under the current rubric. It requires world knowledge that a document-extraction agent should not be expected to have, and the keyword-matching threshold is miscalibrated for descriptions containing domain-specific jargon.

4. Why Couldn't the Editor Improve the Score?

Three compounding factors:

  1. Ceiling effect. The baseline already achieves 94.4% finding recall, 100% on five other dimensions. The only improvable dimensions are finding_recall (+2 findings, worth ~1.4 composite points) and gap_detection (worth 10 points but unwinnable). The theoretical maximum composite with gap_detection locked at 0.0 is ~0.929. The gap to close is only 0.043 points.
  2. Negative-sum edits. The editor's changes added instruction text to a small model (Haiku) that was already near its instruction-following capacity for this task. Round 2 had no effect; round 3 actively degraded recall (from 94% to 73%) and verbatim quality (from 100% to 93%). More instructions did not help — they confused the agent or forced it to spend time on low-value activities, pushing it toward the timeout and degrading output quality.
  3. Editor cannot see the real problem. The skill-gap data showed 2 missed prose findings and gap_detection=0.0. The editor correctly tried to fix finding recall but had no information about WHY gap_detection was zero (the rubric mismatch). It could not know that gap_detection is structurally unwinnable. The editor eventually tried switching models entirely (round 5), which was creative but invalid — the loop is designed to optimize Haiku-specific instructions, not pick models.

5. Options

Option A: Fix the Rubric's Gap Expectations

Effort: Low (30 min) | Impact: Unlocks 10% of composite score

Replace the three "world knowledge" gaps (G001-G003) with gaps that can be detected from the source documents themselves. Examples: "Performance doc mentions WAL mode but doesn't document WAL-mode page size interaction" or "C API doc describes sqlite3_open_v2 flags but doesn't show SQLITE_OPEN_NOMUTEX usage." These are gaps a document scanner CAN identify because they reference content that IS in the docs but is incomplete.

Tradeoff: Changes the benchmark definition, so historical comparisons break. But the current gap_detection is measuring the wrong thing — it tests world knowledge, not extraction quality.

Option B: Increase the Timeout to 600 Seconds

Effort: Trivial (config change) | Impact: Eliminates ~60% of failures

The baseline takes 198s. Round 3 (the only completed non-baseline round with instruction changes) took 363s. A 600s timeout gives 3x the baseline and accommodates instruction bloat. The ESP32-S3 benchmark completes faster (~150s baseline), so this is SQLite-specific.

Tradeoff: Slower iteration. 100 rounds at 600s worst-case = 17 hours vs 8.3 hours at 300s. Consider making timeout benchmark-specific in the config file.

Option C: Add Benchmark-Specific Timeout to Config

Effort: Low (code + config) | Impact: Structural fix for all benchmarks

Add a "timeout_s" field to haiku-sqlite.json (and other benchmark configs). The loop reads this instead of a hardcoded default. SQLite gets 600s; ESP32-S3 keeps 300s. This scales to future benchmarks of varying sizes without needing to pick a single global value.

Tradeoff: Requires a small loop code change, but is forward-compatible and prevents this class of problem from recurring.

Option D: Constrain the Editor's Edit Scope

Effort: Medium (editor prompt change) | Impact: Prevents wasted rounds

The editor in round 5 changed model: haiku to model: sonnet in the agent file — outside the optimization scope. Add constraints to the editor prompt: "Do not change the model field, frontmatter metadata, or tool list. Only modify instruction text." Also add: "The agent's time budget is tight. Do not add new mandatory passes, verification steps, or increase extraction targets — these risk timeout. Prefer rewording existing instructions over adding new ones."

Tradeoff: Limits editor creativity, but prevents wasted rounds on invalid or counterproductive changes. The editor already demonstrated that adding more text hurts Haiku's performance.

Option E: Give the Editor the Gap Scoring Formula

Effort: Low (editor prompt change) | Impact: Enables gap_detection improvement

The editor sees gap_detection: 0.0 but has no idea how the scorer works or what it expects. If the editor knew that gap_detection does keyword matching against specific expected descriptions, it could potentially craft instructions that prime the scout to mention those topics. For example: "After recording gaps from the documents, consider whether the documentation set is missing coverage of common database features like encryption, full-text search, or backup APIs."

Tradeoff: This is "teaching to the test." The agent would be hard-coded to mention specific gaps rather than developing general gap-detection ability. It improves the benchmark number without improving the agent's real-world utility.

6. Recommended Approach

Apply A + C + D together:

  1. Fix the rubric (Option A) so gap_detection measures something achievable from the source documents. This is the single biggest issue — 10% of the composite score is structurally unwinnable.
  2. Add per-benchmark timeout (Option C) so SQLite gets 600s while ESP32-S3 keeps 300s. This prevents 60% of rounds from producing no usable data.
  3. Constrain the editor (Option D) to prevent model-switching and instruction bloat that caused both the regression in round 3 and the timeouts in rounds 4-5.

Skip Option E — it optimizes for the benchmark metric rather than the agent's general capability, which defeats the training loop's purpose.
